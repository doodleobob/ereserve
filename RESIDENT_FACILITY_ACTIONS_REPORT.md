# Resident Facilities actions

1. **Previous behavior.** Both resident card actions were anchors pointing to `facilities.show`. That page displayed facility information and the reservation form together, so View Details and Reserve entered the same flow.

2. **Files changed for this request.** Existing workspace changes were preserved. This request modifies `resources/views/facilities.blade.php`, `resources/views/facility-show.blade.php`, `resources/views/partials/facility-view-modal.blade.php`, `app/Http/Controllers/ReservationController.php`, `bootstrap/app.php`, `public/js/modals.js`, `public/css/app.css`, `public/sw.js`, and `tests/Frontend/facility-layout-fixtures.php`. It adds `resources/views/partials/facility-reservation-form.blade.php`, `tests/Feature/ResidentFacilityActionsTest.php`, `tests/Frontend/resident-facility-actions-browser.cjs`, and this report.

3. **View Details.** The card button opens the existing `partials.facility-view-modal`, now also used for residents. It shows the actual facility name, availability, full description, barangay/location, reservation access, hourly rate, category, capacity, and existing photos. Existing matching barangay/location presentation is retained. Its content is read-only and its footer contains Close and Reserve. Reserve is disabled when the existing catalog flags prohibit booking. The modal does not include reservation fields, management actions, resident identities, reservation IDs/purposes, or internal Official Use details. Admin and Super Admin details retain their Close-only footer.

4. **Direct Reserve.** The card's Reserve button opens the reservation modal for that card's facility immediately. The facility name is shown, and its slug is already bound to the existing reservation endpoint. There is no facility selector. Both card buttons remain visible, including for restricted and unavailable facilities, with Reserve disabled and the reason displayed.

5. **Details to Reserve.** The details footer targets the same reservation modal as the card. The shared modal controller closes and cleans up Details before opening Reservation, preserving the original card trigger for focus restoration. Only one dialog remains open, with the shared background scroll lock applied. Cancel closes the form and resets its fields.

6. **Shared modal design.** Both dialogs use the existing `resources/views/components/modal.blade.php` (`<x-modal>`) and `EReserveModal`. Shared header, close control, backdrop, validation rendering, busy state, duplicate-submit prevention, refresh, and toast behavior are reused. The shared controller adds an explicit `data-modal-transition` option for switching dialogs. Existing gallery markup and `facility-gallery.js` remain the image implementation, including aspect-preserving images and multiple-photo controls.

7. **Shared reservation workflow.** The original form from `facility-show.blade.php` is extracted into `partials.facility-reservation-form.blade.php`, used both by the existing page and the new modal. Field names, required fields, capacity constraints, overnight help, CSRF protection, and endpoint stay the same. Both entry points POST to `reservations.store` and execute `ReservationController::store`. That method adds a JSON success response after the existing creation transaction; regular form submissions retain their redirect and flash message. The existing exception-response configuration includes `reservations.store` so modal requests receive JSON validation errors. Existing access/status checks, row locking, capacity/date/time validation, duplicate guards, rate snapshot, notifications, and Official Use conflict validation are retained. No reservation or availability implementation is duplicated.

8. **Responsive changes.** Resident card actions reuse primary/secondary button styles with equal padding, typography, radius, widths, and at least 44px touch height. They wrap into balanced rows when needed. Details keeps its existing scrolling body and fixed header/footer. The reservation body scrolls within the viewport, while header and actions stay accessible; time fields and actions stack on small screens. IDs and labels are scoped to each facility. Browser checks cover 1280, 768, 640, 390, 320, and 240px widths, with viewport heights as short as 400px. Facility filtering uses document events and current DOM queries so it still works after a booking refresh. The PWA static cache advances to v14 for the updated modal script.

9. **Tests added/updated.** Nine new PHP tests cover different dialog targets, read-only facility data/gallery, correct selected facility and existing endpoint/form, unavailable/restricted resources, JSON creation and duplicate guards, regular redirect behavior, field validation, Official Use blocking in both response formats (including overnight and conflict status), adjacent slots, resident privacy, and Close-only management details. The shared in-memory fixture generator adds a resident browsing another barangay. Twelve new headless Chrome scenarios cover local/cross-barangay residents across six viewport sizes, balanced/touch-size actions, read-only Details, galleries, transitions, correct forms and labels, disabled booking, cancel/reset/focus, validation, duplicate submits, busy Escape protection, submission from both entry points, toast/refresh, and filtering after refresh. Existing card, gallery/details, and JavaScript regression checks also ran.

JavaScript suite: **22 passed**. New resident browser scenarios: **12 passed**. Existing facility card browser scenarios: **20 passed**. Existing details/gallery browser scenarios: **18 passed**. PHP Pint, JavaScript syntax checks, and `git diff --check`: **passed**.
